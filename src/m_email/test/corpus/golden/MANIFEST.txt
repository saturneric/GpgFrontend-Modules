Golden MIME corpus for the e-mail module
========================================

Hand-authored .eml messages used by gf_mod_email_test. This is the bucket
GpgFrontend owns: it is a specification, and it carries byte-level contracts.
Messages taken from third-party suites live in ../public/ under looser rules
(see ../public/MANIFEST.txt); their provenance is in ../PROVENANCE.md. Unlike the OpenPGP
vectors under resource/lfs/test/, these are not generated by an external tool:
the artifact here IS the hand-written MIME, so a generator script would only
add indirection around string literals. Edit the files directly and keep this
manifest in step.

Conventions
-----------
* All files use CRLF line endings, as real messages do. Byte-exact assertions
  (raw header slices, signature region offsets, byte preservation) depend on
  this -- do not let an editor normalize them to LF. The corpus is marked
  -text in .gitattributes so a checkout cannot convert it either, and
  GoldenFixturesKeepTheirCrlfLineEndings fails if that protection is ever
  missing. 16-signed-lf-mangled.eml is the single deliberate exception.
* The OpenPGP armor in these files is a placeholder, not real cryptography.
  The corpus exercises MIME parsing, structure classification and coverage
  attribution; it never asserts that anything verifies.
* Nothing here reaches the network, and no file contains a real key or a real
  signature.

Messages
--------
01-plain-text.eml
    text/plain only. The degenerate tree: root is the body, no children.
    Security state: kPLAIN.

02-alternative.eml
    multipart/alternative { text/plain, text/html }. Both members are body
    candidates and share one alternative_group. SelectBodyPart() picks the
    plain form by default and the HTML form when prefer_html is set.
    ExtractParts(), which is kept byte-compatible with its historic rule,
    picks the text/plain member; the html member becomes an attachment.
    Security state: kPLAIN.

03-mixed-attachments.eml
    multipart/mixed { text/plain, application/pdf, text/csv }. Body plus two
    named attachments, in part order. Security state: kPLAIN.

04-pgpmime-signed.eml
    Well-formed RFC 3156 multipart/signed, micalg=pgp-sha256. One region
    (region_id 0, nesting_depth 0) covering the text/plain part in full. The
    application/pgp-signature part is a protocol part: never an attachment and
    never covered. Security state: kSIGNED.

05-pgpmime-encrypted.eml
    Well-formed multipart/encrypted with the Version: 1 control part. Subject
    is the "..." placeholder the module writes when encrypting. No regions.
    Security state: kENCRYPTED.

06-signed-inside-encrypted.eml
    multipart/mixed { multipart/encrypted, multipart/signed }. Both structures
    present side by side, which is the ambiguous shape worth naming in the UI.
    One region, from the multipart/signed, micalg=pgp-sha512.
    Security state: kSIGNED_ENCRYPTED.

07-inline-cid-image.eml
    multipart/related { text/html, image/png with Content-ID }. The image's
    content_id is parsed WITHOUT angle brackets, which is the form a
    "cid:" URL in the HTML actually references. Security state: kPLAIN.

08-encoded-words.eml
    RFC 2047 encoded-words in From, Subject and an attachment filename, all
    non-ASCII. Exercises decoding into header_fields and into
    EMailAttachment::filename. Security state: kPLAIN.

09-hostile-filenames.eml
    Attachment names chosen to attack the save path: a path traversal
    ("../../../../etc/passwd"), a Windows reserved device name ("CON.txt"),
    and the same name twice ("report.pdf") to force deterministic numbering.
    Feeds SanitizeAttachmentFileName() and UniqueAttachmentFileNames().
    Security state: kPLAIN.

10-pgp-keys-attachment.eml
    application/pgp-keys attachment, which the UI offers to import rather than
    save. is_openpgp_key is true for that part only. Security state: kPLAIN.

11-nested-signatures.eml
    multipart/signed { multipart/signed { text/plain, sig }, sig }. Two
    regions: the outer (region_id 0, nesting_depth 0, micalg pgp-sha256) and
    the inner (region_id 1, nesting_depth 1, micalg pgp-sha512). The text/plain
    part is covered by BOTH, so covered_by_regions is [0, 1], outermost first.
    This is the message a single coverage boolean cannot describe.
    Security state: kSIGNED.

12-odd-headers.eml
    Two Received: headers with tab continuation lines, a folded To:, a
    duplicated X-Custom:, and a Reply-To pointing at an unrelated domain. The
    raw header slice must preserve order, folding and duplication exactly;
    the decoded view may not. Security state: kPLAIN.

13-signed-micalg-mismatch.eml
    multipart/signed declaring micalg=pgp-sha512. Paired with a verify result
    reporting SHA256, this is the declared-vs-actual disagreement that sets
    EMailSignatureResult::micalg_mismatch. Parsing alone cannot detect it --
    the region only records what was declared. Security state: kSIGNED.

14-signed-with-attachment.eml
    multipart/mixed { multipart/signed { multipart/mixed { text, covered.bin },
    sig }, uncovered.bin }. The realistic shape of a signed message carrying an
    attachment, plus one appended outside the signature. covered.bin has a
    non-empty covered_by_regions; uncovered.bin does not.
    Security state: kSIGNED.

15-empty-body-parts.eml
    First text/plain part is empty, so the historic "first text/plain wins"
    rule falls through to the second. Also carries a Content-Disposition:
    attachment with no filename. Security state: kPLAIN.

16-signed-lf-mangled.eml
    04-pgpmime-signed.eml with the signed entity's line endings normalised to
    bare LF, the way a program that rewrites line endings on save leaves a
    message. The headers and the rest of the message stay CRLF, because only
    the signed part is damaged in the real case. The signature can no longer
    verify over these bytes, which is indistinguishable from a forgery unless
    the cause is reported; HasBareLineFeeds detects it and InspectMessage
    reports it. Security state: kSIGNED.

17-encrypted-inside-signed.eml
    multipart/signed { multipart/encrypted { version, ciphertext }, sig }.
    Encrypt-then-sign: the entity under the signature IS the encrypted block,
    so the signature is over ciphertext. It says who passed the blob along and
    nothing about who wrote what is inside it -- signing a copy of someone
    else's ciphertext takes none of their keys. The region records this as
    covers_ciphertext_only and InspectMessage reports it.
    Note that this classifies as kSIGNED_ENCRYPTED, exactly like 06, which
    places an encrypted and a signed section side by side. The security state
    cannot tell the two orderings apart; the regions can. Nothing built on the
    state alone may make a claim about provenance.
    Security state: kSIGNED_ENCRYPTED.

A note on what these fixtures can prove
---------------------------------------
Nothing here verifies. The armor is a placeholder and this test target links
Qt Core and vmime only -- no gpgme, no SDK -- so every assertion is about
SHAPE. "Covered by a signature region" means structurally inside a signed
subtree. It does not mean authenticated, and no test may be written or read as
if it did. Real signature and decryption behaviour needs the crypto path in
EMailBasicGpgOpera.cpp, which is still untested and needs a gpgme-enabled
target of its own.

Known divergences from the pre-tree implementation
--------------------------------------------------
The differential test compares ExtractParts() against ExtractPartsLegacy(),
the walker that preceded the MIME tree, across every message above. One
deliberate divergence exists:

  Coverage of a sibling of the signed entity.
    The legacy walker marked EVERY descendant of a multipart/signed as being
    inside the signed part. RFC 3156 signs only the FIRST part; a second,
    non-signature part is not covered. Marking it covered lets an attacker
    append content to a signed message and have it inherit the signature, so
    the tree implementation attributes coverage to the first part only.
    No corpus message triggers this divergence, because every signed message
    here is well-formed; it is pinned directly by the unit test
    SiblingOfTheSignedEntityIsNotCovered.

Everything else -- body bytes, body content type, and the attachment sequence
(count, order, filenames, MIME types, dispositions, is_openpgp_key and decoded
bytes) -- must agree exactly.
